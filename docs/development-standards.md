# Стандарты разработки и архитектурные рекомендации проекта «Светлый»

Данный документ представляет собой свод правил и лучших практик (Single Source of Truth) для поддержания чистоты кода, легкой масштабируемости и производительности на уровне Senior-разработки.

---

## 1. Соглашение об именовании файлов и папок (Naming Conventions)

Для обеспечения единообразия в проекте используется строго **kebab-case** для всех типов файлов и директорий:

*   **Компоненты:** `pet-card.tsx`, `pets-grid.tsx`, `layout-footer.tsx` (вместо `PetCard.tsx` или `petsGrid.tsx`).
*   **Утилиты/Хелперы:** `format-age.ts`, `normalize-pet-data.ts`.
*   **Папки страниц и компонентов:** `components/pets/`, `lib/helpers/pets/`.
*   **Стили:** `globals.css`, `index.css`.

> [!IMPORTANT]
> Имена файлов пишутся исключительно строчными буквами с разделением слов через дефис. Это гарантирует отсутствие проблем с чувствительностью к регистру (Case Sensitivity) на различных операционных системах (Windows, Linux, macOS) в Git и CI/CD-процессах.

## 2. Архитектурная структура и разделение обязанностей

Проект делится на четкие слои абстракции:

```
lightyar/
├── app/                  # Routing Layer (Маршрутизация и Server Components)
├── components/           # Presentation Layer (Компоненты отображения)
│   ├── ui/               # Атомарные UI-элементы общего назначения (кнопки, скелетоны)
│   └── [feature]/        # Странично-зависимые компоненты (напр. components/pets/)
├── lib/                  # Core & Logic Layer (Бизнес-логика, API и Хелперы)
│   ├── api/              # Клиент для работы с API (Strapi Client, сервисы и типы)
│   └── helpers/          # Утилиты и хелперы (каждая функция в отдельном файле!)
└── docs/                 # Документация проекта
```

### 2.1. Routing Layer (`app/**/page.tsx`)
Страницы в Next.js App Router являются **чистыми оркестраторами** данных:
*   Они должны быть легкими серверными компонентами (Server Components).
*   **Запрещено** описывать сложные JSX-блоки разметки, сетки или детали интерфейса прямо в файле страницы.
*   **Запрещено** описывать логику форматирования, расчет возраста, маппинг API-данных или константы заглушек картинок в файле страницы.
*   **Обязанность страницы:** считать параметры поиска (`searchParams`), вызвать соответствующий сервис API, обработать ошибки подключения, передать данные на нормализацию хелперам и собрать страницу из высокоуровневых компонентов.

### 2.2. Presentation Layer (`components/`)
Компоненты разделяются по принципу слабой связанности (Low Coupling) и высокой зацепления (High Cohesion):
*   Любой крупный блок (например, Hero-секция с видео, список карточек, модальное окно) выносится в отдельный изолированный компонент в папке соответствующей фичи (например, `components/pets/pets-hero.tsx`).
*   Если элемент повторяется или содержит сложную верстку (например, карточка животного), он выделяется в отдельный файл (`components/pets/pet-card.tsx`).
*   Компоненты должны быть самодостаточными, принимать строго типизированные `props` и не делать самостоятельных тяжелых внешних fetch-запросов (если они не являются независимыми интерактивными островами Client Components).

### 2.3. Modular Logic Layer (`lib/helpers/`)
В соответствии с корпоративными практиками больших систем:
*   **Один хелпер/утилита — один файл.** Например, функция расчета возраста создается в `lib/helpers/pets/calculate-age-in-years.ts`.
*   Это позволяет:
    1.  Иметь абсолютно чистые и понятные пути импорта.
    2.  Эффективно оптимизировать бандл (Tree Shaking) на этапе сборки Next.js.
    3.  Писать изолированные, понятные unit-тесты для каждой функции.
    4.  Быстро ориентироваться в кодовой базе при ее разрастании до сотен утилит.

## 3. Правила написания компонентов и типизация

*   Каждый компонент должен экспортировать интерфейс своих пропсов:
    ```tsx
    interface PetCardProps {
      pet: MappedPet;
      priority?: boolean;
    }
    
    export function PetCard({ pet, priority = false }: PetCardProps) { ... }
    ```
*   Избегайте `export default` для UI-компонентов. Используйте именованные экспорты (`export function PetCard`), чтобы облегчить автоимпорт в редакторах и исключить путаницу с именами при рефакторинге. (Исключение — файлы страниц Next.js `page.tsx` и `layout.tsx`, где Next.js жестко требует `export default`).
*   Используйте семантическую верстку (теги `<article>`, `<section>`, `<ul>`, `<li>` с корректными `aria-label`).
*   Стилизация: используйте чистый Vanilla CSS или TailwindCSS (строго по договоренности). Цвета должны браться из единой палитры, избегайте хаотичных инлайн-стилей.

## 4. Пример идеального рефакторинга каталога питомцев

Для наглядности, новая структура каталога питомцев после рефакторинга выглядит так:

1.  **`app/pets/page.tsx`** — легкий серверный контроллер (около 60 строк вместо 390!).
2.  **`lib/helpers/pets/normalize-pet-data.ts`** — чистый маппер данных из формата Strapi API во внутреннее плоское представление, удобное для верстки.
3.  **`components/pets/pet-card.tsx`** — визуальное представление карточки питомца.
4.  **`components/pets/pets-grid.tsx`** — компонент сетки, управляющий Bento-стилем первого и шестого элемента, а также показывающий пустое состояние «Питомцев не найдено».
5.  **`components/pets/pets-hero.tsx`** — изолированная премиальная обложка с фоновым видео и счетчиками.
6.  **`components/pets/catalog-unavailable.tsx`** — изолированный экран системной ошибки API.
